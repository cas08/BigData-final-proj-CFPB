# Журнал кроків

Тут записано, що я робив, у тому порядку, як робив, з командами і результатами. Номер кроку збігається з префіксом файлу: крок 5 це `scripts/05_job.py`, крок 11 це `docs/11_estimates_vs_fact.md`. Усі команди запускаються з каталогу проєкту. Spark друкує багато рядків WARN, тому повні логи запусків на всіх даних я зберіг в `evidence/`.

## Що змінилось порівняно з PLAN.md

- На повних даних у плані виявилось 4 shuffle, а не 3: оптимізатор спершу вибрав SortMergeJoin (крок 11).
- На вибірці перший stage має 4 задачі читання, а не 1, бо малий файл Spark ділить на частини за кількістю ядер.
- У кроці 9 я додатково поміряв розмір колонок Parquet (`--sizes-only`), бо метрика Spark «Input» для Parquet показувала занижене значення.

## 0\_ Дані і середовище

Повний датасет я завантажив з сайту CFPB (`complaints.csv.zip`, версія від 2026-11-16) і розпакував. Вийшов `complaints.csv` на 5,82 ГБ і 19 203 798 рядків. Розмір і sha256 записав у `data/SOURCE.md`. Файл лежить у `data/` поруч із вибіркою, але до здачі не входить: замість нього там посилання і контрольна сума. Docker підключає `data/` як `/data`, тому в командах повний файл називається `/data/complaints.csv`.

Середовище взяв те саме, що в практичних 6-7: Docker Compose з образом `apache/spark:4.2.0-python3`. Сервіс `job` запускає скрипти, сервіс `history` піднімає History Server. У `conf/spark-defaults.conf` стоїть `local[4]`, driver 2 ГБ і event log у `spark-events/` без стиснення. Правила чистки й визначення relief я записав один раз у `scripts/rules.py`, і їх використовують і Python-скрипти, і Spark (`scripts/common.py`).

Spark, а не Hadoop MapReduce, я обрав тому, що задача має 3 агрегації і join, які йдуть одна за одною. У MapReduce це були б 3-4 окремі job-и із записом проміжних результатів на диск. Spark виконує все одним планом, сам робить часткову агрегацію (combiner) і broadcast join, а EXPLAIN і stage-і в UI потрібні для карти фаз.

Перевірка, що контейнер працює і правила правильні:

```bash
docker compose run --rm job python3 scripts/rules.py
```

Виводить `rules OK`: правила проганяються на кількох штучних рядках.

## 5\_ Основний конвеєр (етапи 1-4)

`scripts/05_job.py` складається з функцій `stage1`-`stage4`, кожна займає кілька рядків DataFrame API. Єдина дія, `collect()`, повертає ~20 тис. пар (компанія, продукт), а далі Python сортує їх і пише рейтинг. План виконання (EXPLAIN) скрипт зберігає до запуску і після.

```bash
docker compose run --rm --service-ports job
docker compose run --rm -T job spark-submit scripts/05_job.py --input /data/complaints.csv --tag full
```

На вибірці застосунок працює 5,9 с: 2 548 пар, у рейтинг потрапили 3 бюро (очікуваний вивід є в README). На повних даних застосунок працює 19,4 с, з них дія 16,5 с: 20 232 пари, у рейтингу 498 (`out/05_result_full.csv`).

Перший запуск упав з `AMBIGUOUS_REFERENCE`. Spark SQL не розрізняє регістр імен колонок, і `N` (норма категорії) зіткнулась з `n` (скарги компанії). Я перейменував норму на `cat_n` / `cat_r`. Невдалий запуск лишився в `spark-events/`.

У плані (`out/05_plan_*.txt`) на вибірці видно 3 Exchange (shuffle №1-№3) і BroadcastExchange, а CSV читається один раз (`ReusedExchange`). На повних даних початковий план мав SortMergeJoin, і AQE переключився на broadcast уже після зайвого shuffle. Докладніше в кроці 11.

## 8\_ Перекіс

Для кожного shuffle порахував найчастіший ключ, медіану і частку топ-10: у скаргах і в рядках, які йдуть у shuffle.

```bash
docker compose run --rm -T job spark-submit scripts/08_skew_stats.py --input /data/complaints.csv --tag full
```

Результат (`out/08_skew_full.md`):

| Shuffle                                       | Одиниця                              | Найчастіший ключ                                              | Max       | Медіана | Топ-10 |
| --------------------------------------------- | ------------------------------------ | ------------------------------------------------------------- | --------- | ------- | ------ |
| №1                                            | скарги                               | TransUnion / кредитні звіти / Incorrect information / 2026-07 | 128 564   | 1       | 6,5 %  |
| №2                                            | скарги                               | кредитні звіти / Incorrect information / 2026-07              | 364 751   | 34      | 17,4 % |
| №2 і зайвий shuffle для join (той самий ключ) | рядки етапу 1 (компаній у категорії) | Debt collection / Attempts to collect debt not owed / 2026-04 | 716       | 14      | 0,9 %  |
| №3                                            | скарги                               | TransUnion / кредитні звіти                                   | 5 045 943 | 4       | 79,8 % |
| №3                                            | рядки етапу 3 (клітинок)             | Capital One / Credit card                                     | 3 171     | 3       | 3,7 %  |

Зайвий shuffle для join має той самий ключ, що й №2, але йде без часткової агрегації, тому записів на ключ у ньому стільки ж, скільки рядків етапу 1 (max 716).

Розміри задач беру з кроку 7, shuffle read на задачу, медіана / max: stage 2 і 3 мають 13,3 / 13,6 МБ, stage 6 має 1,0 / 1,2 МБ, stage 9 (зайвий shuffle) 7,8 / 8,0 МБ, stage 13 1,3 / 1,7 МБ. Тривалість задач у reduce-stage-ах відрізняється не більше ніж на 25 %. У stage-і читання найдовша задача йде 2,7 с проти медіани 1,3 с, але причина там у тому, що шматки по 128 МБ мають від 160 до 660 тис. рядків.

Отже, перекіс у даних великий (TransUnion і кредитні звіти дають 80 % скарг етапу 4), а в shuffle майже не потрапляє: часткова агрегація перетворює мільйони скарг TransUnion на кілька тисяч записів. Окремих заходів проти перекосу я не робив, бо вони не знадобились.

Запис лежить у `evidence/demo_sample.mov` на випадок, якщо демо на захисті не запуститься. На ньому:
